# 프론트엔드 iOS 가이드

## 기술 맥락

- frontend는 Swift 기반 iOS 앱이다.
- 초기 구조는 전역 `view`, `viewModel`, `service`, `model`를 두는 단순 layered 구조를 따른다.
- 화면 표현, 사용자 입력, 상태 표시, backend 응답 소비를 명확히 분리한다.
- backend가 API 계약과 비즈니스 의미의 source of truth다.

## 구조 원칙

- 패키지는 전역 레이어 기준으로 나눈다.
- 기본 구조는 `view`, `viewModel`, `service`, `model`을 기준으로 나눈다.
- 화면 UI 코드는 `view` 아래에 둔다.
- 화면 상태와 사용자 액션 흐름은 `viewModel`에서 처리한다.
- API 호출, 응답 디코딩, 앱 내부 모델 변환은 `service`에서 처리한다.
- `service/dto`는 backend 응답 디코딩 전용 모델을 둔다.
- `model`은 앱 내부에서 공통으로 사용하는 모델을 둔다.
- backend DTO와 앱 내부 모델은 구분한다.
- 공통 로직은 실제로 공통성이 확인된 경우에만 `common`으로 올린다.
- 구조는 단순하게 시작하되, 나중에 기능별 구조로 진화할 수 있도록 응집도를 유지한다.

## 구현 규칙

- backend가 제공한 계약 필드와 의미를 client-side에서 다시 계산하지 않는다.
- 기존 화면과 기존 흐름을 먼저 확장하고, 불필요한 새 화면이나 새 상태 흐름 추가는 마지막 수단으로 본다.
- backend가 내려준 상태 값, 에러 코드, 의미 필드는 그대로 사용하고, 화면은 이를 표시하는 역할에 집중한다.
- service는 backend DTO를 디코딩한 뒤, 앱 내부 모델로 변환해서 반환한다.
- viewModel은 backend DTO를 직접 사용하지 않고, 앱 내부 모델을 기준으로 화면 상태를 구성한다.
- service는 response decoding과 앱 내부 모델 변환까지 담당하고, viewModel은 화면 상태와 사용자 액션 흐름에 집중한다.
- backend가 source of truth인 값에 대해서 local fallback으로 의미를 바꾸지 않는다.
- unsupported 상태를 조용히 기본값으로 바꾸지 않는다.
- nil 가능성은 불필요하게 넓히지 않는다.
- response decoding, 화면 상태 계산, UI 표시 로직을 한 함수나 한 타입에 섞지 않는다.

## 상태 관리 규칙

- view는 표시와 사용자 입력 전달에 집중한다.
- viewModel은 화면 상태, 로딩, 에러, 성공 상태 전이를 관리한다.
- service는 네트워크 호출과 응답 처리만 담당하고, UI 상태를 직접 알지 않는다.
- backend 의미를 다시 계산하는 정책 로직은 view나 viewModel에 넣지 않는다.
- 같은 의미를 여러 곳에서 중복 계산하지 않는다.
- 화면 상태는 읽는 사람 입장에서 바로 이해되도록 명시적으로 표현한다.
- 화면 상태는 가능한 한 명시적인 enum 또는 동등한 명시 구조로 표현한다.
- 로딩, 빈 상태, 오류 상태, 성공 상태를 여러 boolean으로 흩어 놓기보다 하나의 읽기 쉬운 상태 모델로 표현한다.
- navigation 의도는 viewModel에서 관리하고, 실제 화면 전환은 view에서 수행한다.

## 네트워크 / 계약 규칙

- backend 응답 구조와 필드 의미는 backend를 기준으로 해석한다.
- backend DTO는 service 경계 안에서만 사용하고, 화면 계층으로 직접 올리지 않는다.
- backend 응답이 변경되면 service가 먼저 그 차이를 흡수하고, viewModel과 view에는 필요한 앱 내부 모델만 전달한다.
- enum 값, 상태 값, 에러 코드는 임의로 변경하거나 재해석하지 않는다.
- backend 응답이 additive하게 확장되면, 기존 소비 방식은 유지하고 필요한 표시만 추가한다.
- not-found, validation failure, unsupported-state, conflict 같은 실패는 backend 계약 기준으로 분기한다.
- 클라이언트는 backend 계약의 빈자리를 임의의 의미로 메우지 않는다.

## 오류 처리 규칙

- backend가 제공한 `errorCode`를 우선적으로 사용한다.
- 사용자 노출 메시지와 내부 분기 기준을 혼합하지 않는다.
- 화면은 실패 상태를 명시적으로 보여주고, 조용히 성공처럼 보이게 만들지 않는다.
- 네트워크 실패, 디코딩 실패, backend business failure를 구분해서 처리한다.
- 예상하지 못한 내부 오류는 공통 오류 상태로 처리하고, backend 계약과 충돌하는 임의 의미를 만들지 않는다.

## 검증 규칙

- 사용자 입력 형식 검증은 화면 입력 경계에서 처리한다.
- 필수값, 형식, 기본적인 입력 제약은 view 또는 viewModel의 입력 처리 경계에서 검증한다.
- 비즈니스 규칙 판단은 frontend가 새로 만들지 않고 backend 기준을 우선한다.

## 시간 / 표시 규칙

- 시간 의미, 날짜 경계, 상태 의미는 backend 기준을 우선한다.
- iOS는 사용자 locale과 화면 요구사항에 맞는 formatting을 담당한다.
- 시간 표시 formatting과 비즈니스 의미 계산을 섞지 않는다.
- 상대 시간, 날짜 문자열, 시간 문자열은 화면 표시 목적에 한해 iOS에서 변환한다.

## 비동기 규칙

- 비동기 처리는 `async/await`를 기본으로 사용한다.
- UI 상태 반영은 main thread 기준으로 일관되게 처리한다.
- 비동기 호출 흐름, 에러 처리, 상태 갱신을 한 곳에 과도하게 섞지 않는다.
- 취소 가능성이 있는 작업은 화면 생명주기와 맞는 방식으로 명시적으로 관리한다.

## 테스트 기대치

- 테스트는 `unit test`와 `integration test` 두 종류로 구분한다.
- unit test는 viewModel의 상태 전이, 표시 규칙, 변환 로직을 빠르게 검증하는 데 사용한다.
- integration test는 view, viewModel, service, decoding, 에러 처리 흐름이 함께 동작하는 경로를 검증하는 데 사용한다.
- backend 계약 소비 방식이 바뀌면 integration test를 추가한다.
- 핵심 화면 상태 전이와 회귀 위험이 큰 로직은 unit test로 고정한다.
- mocking은 경계 분리와 테스트 목적이 분명할 때만 사용한다.
- 과도한 mocking으로 구현 세부에 강하게 결합되는 테스트는 피한다.
- 로딩, 빈 상태, 오류 상태, 성공 상태, backend business failure 같은 경계 케이스를 명시적으로 검증한다.
- 테스트는 기대 동작과 실패 동작이 읽히는 형태로 작성한다.

## 코드 구성 원칙

- 함수는 하나의 역할만 수행하도록 작성한다.
- 함수는 가능한 한 짧고 읽기 쉽게 유지하며, 기본적으로 15줄 내외를 목표로 한다.
- 깊은 들여쓰기와 중첩 조건문을 피하고, guard와 early return을 우선 사용한다.
- 조건 분기가 복잡해지면 의미 있는 보조 함수나 computed property로 분리한다.
- 분리된 함수 이름만 읽어도 상위 흐름이 이해되도록 작성한다.
- helper 함수는 단순 줄 수 감소가 아니라 책임 분리를 위해서만 도입한다.

## 가독성 원칙

- 코드는 가능한 한 선언적으로 읽히도록 작성한다.
- 무엇을 표시하는지, 어떤 상태인지, 어떤 조건에서 중단하는지가 구조만 봐도 드러나야 한다.
- 컬렉션 변환, 필터링, 정렬은 읽기 쉬운 경우에 한해 선언형 표현을 우선한다.
- 선언형 표현이 오히려 이해를 어렵게 만들면 단순한 명령형 코드를 사용한다.
- 여러 단계의 조건 분기보다 이름 있는 조건과 작은 함수 조합을 우선한다.
- 들여쓰기 레벨이 깊어지기 시작하면 구조를 다시 나누는 것을 우선 검토한다.
- 한 함수 안에서 3단계 이상 중첩이 생기면 구조 분리를 우선 검토한다.
- `if/else` 사슬보다 빠른 실패 반환과 명시적 분기를 우선한다.
- boolean 조건은 인라인 복합식보다 의미 있는 이름으로 드러낸다.

## 네이밍 규칙

- 함수명과 필드명은 역할과 의미가 이름만으로 직관적으로 드러나야 한다.
- 추상적인 이름보다 구체적인 동사와 대상을 사용한다.
- `process`, `handle`, `execute`, `data`, `flag`, `manager`, `helper`, `util` 같은 포괄적 이름은 특별한 이유가 없으면 피한
다.
- boolean 필드는 `is`, `has`, `can` 접두를 사용해 의미가 드러나게 작성한다.
- 컬렉션 이름은 복수형으로 작성하고, 타입명보다 의미를 우선한다.
- ViewModel, 화면 상태, 에러 코드, DTO 이름은 사용 맥락과 역할이 바로 드러나야 한다.
- exact 의미가 중요한 값은 축약보다 명확성을 우선한다.

# 리뷰 대상 선택

## 브랜치 또는 미커밋 변경

1. `git rev-parse --show-toplevel`로 root를 확인하고 사용자가 이미 지정한 항목을 반영한다.
2. 범위가 없으면 브랜치 비교 또는 미커밋 변경을 선택하게 한다.
3. 브랜치 비교에서 기준이 없으면 `git for-each-ref`로 `refs/heads/`와 `refs/remotes/`의 실제 이름을 조회한다. 원격 HEAD 같은 심볼릭 참조는 제외하고 local/remote 구분을 유지한다.
4. 선택한 참조를 커밋 SHA로 확인하고 HEAD 및 merge base를 고정한다. 참조가 없거나 공통 조상이 없으면 임의의 기준으로 대체하지 않는다.
5. 브랜치 리뷰는 merge base → HEAD의 변경을 검토한다. 미커밋 변경은 자동 포함하지 않는다. 필요한 코드·테스트 원문도 같은 커밋에서 확인한다.
6. 미커밋 리뷰는 index와 작업 트리의 diff 및 `git ls-files --others --exclude-standard`로 확인한 파일을 포함한다. 부분 staging이 있으면 index와 작업 트리의 차이를 기록하고, HEAD 대비 최종 작업 트리를 기본 동작 검토 대상으로 삼는다. 사용자가 staged-only를 지정하면 index를 기준으로 한다.

자동 fetch나 branch checkout은 하지 않는다. 저장된 원격 추적 브랜치는 서버의 최신 상태와 다를 수 있으므로 결과에 사용한 SHA를 남긴다. Git 명령에는 조회한 ref를 안전하게 인자로 전달하고 revision과 파일 경로를 구분한다.

브랜치 리뷰 중 작업 트리가 dirty하면 `git show`·`git grep` 등으로 대상 커밋의 원문을 조회한다. dirty 파일로 실행한 테스트를 대상 커밋의 검증 결과로 표시하지 않는다. 미커밋 리뷰에서는 읽은 파일의 내용·해시와 상태를 종료 시 확인하고 바뀐 부분의 분석을 갱신한다.

## 선택 화면

현재 환경·모드에서 사용 가능한 선택형 질문 도구로 실제 후보를 표시하고 답변을 기다린다. 기본 선택은 답변이 아니다. 비동기 질문을 보냈으면 답변 도착 전에는 선택에 의존하는 리뷰를 진행하지 않는다.

후보가 도구의 선택지 제한보다 많으면 추가 후보 보기로 나누거나 범위를 좁힌다. 목록에 없는 이름을 만들지 않는다. 선택형 도구를 사용할 수 없으면 현재 환경이 허용하는 대화형 질문으로 선택을 받는다. UI를 위해 실행 모드를 임의로 변경하지 않는다.

## 명세 참조: 사용자 요청 시에만

기본 리뷰에서는 OpenSpec을 탐색하거나 선택을 묻지 않는다. 명세 참조를 요청한 경우에만 다음을 수행한다.

- root의 `openspec/changes/` 바로 아래 변경 디렉터리 이름을 목록으로 보여준다. `archive/`는 기본 후보에서 제외한다.
- 직접 지정한 명세는 다시 묻지 않는다. 여러 변경을 추가 선택하거나 명세 없이 진행할 수 있게 한다.
- 후보 경로가 없으면 그 사실을 알려 명세 없이 진행한다. 사용자가 특정 명세를 필수로 요구했는데 접근할 수 없으면 명세 검증이 미완료임을 표시한다.
- 선택한 변경의 실제 proposal, design, delta spec, tasks에서 관련 부분을 읽는다. delta 해석에 필요한 `openspec/specs/`의 기존 요구사항도 확인한다. 문서 전체의 존재나 현재 diff와 같은 버전임을 가정하지 않는다.
- PR 설명이나 사용자 지정으로 이번 PR의 구현 범위를 확인한다. diff와 tasks의 완료 체크만으로 이번 PR의 약속을 추정하지 않는다.
- 전체 명세는 설계 맥락으로 활용하고, 누락 검증은 이번 PR 범위가 확정된 요구사항에 한정한다. 범위가 불명확하면 맥락으로만 참조하고 그 사실을 결과에 기록한다.
- 사용자가 명세 완료 검증을 요청했는데 범위가 불명확하면 관련 작업·요구사항 선택을 받는다.
- 후속 PR에 배정된 기능의 부재는 누락이 아니다. 현재 PR이 기존 계약을 깨거나 실행에 필수적인 의존성을 빠뜨렸는지는 별도로 확인한다.

명세는 기대 동작에 대한 근거다. tasks 완료 표시나 구현자가 작성한 설명을 실제 동작의 증거로 간주하지 않는다. 문서 간 충돌은 임의로 해결하지 않고 영향 범위와 확인 질문을 남긴다.

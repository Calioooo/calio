# 프로젝트 코드 리뷰

## 실행 원칙

단일 에이전트가 범위 확정 → 변경 흐름 파악 → 후보 탐색 → 반증과 검증 → 결과 작성을 수행한다. 서브 에이전트를 호출하지 않는다. 재검토는 같은 에이전트의 검증 단계이며 독립 리뷰와 동일하다고 간주하지 않는다.

구현 지침의 원본은 프로젝트 문서다. 이 스킬은 지적을 발견하고 검증하는 방법을 정한다. 코드·설정 수정, formatter 적용, 커밋과 외부 댓글 작성은 수행하지 않는다. 필요한 최소 재현은 허용된 임시 위치에서 수행하고 작업 트리는 유지한다.

## 1. 비교 대상 고정

[리뷰 대상 선택](references/review-scope.md)을 읽고 범위와 기준 브랜치를 확정한다. 실제 브랜치 목록으로 선택을 받는다. OpenSpec은 사용자가 참조를 요청한 경우에만 같은 문서의 명세 절차를 따른다.

기준·대상 SHA와 비교 방식을 기록한다. 브랜치 리뷰는 merge base부터 HEAD까지, 미커밋 리뷰는 staged·unstaged·untracked 변경을 포함한다. 이후 코드 탐색과 검증도 같은 버전을 사용한다.

## 2. 변경을 실행 흐름으로 묶기

먼저 파일 목록과 diff 전체를 훑어 새 동작, 수정, 삭제, 이동, 설정·계약 변경을 구분한다. 포맷·이동이 섞였으면 이전 구현과 비교해 실제 의미가 달라진 부분을 찾는다. 파일 크기만으로 검토 대상을 생략하지 않는다.

관련 파일을 하나의 동작 단위로 묶는다. 예: 요청 DTO 변경, Service 호출, Entity 변경과 응답 변환을 동일한 유스케이스로 연결한다. 각 단위에 다음 사실을 짧게 정리한다.

- 변경 전후 동작과 근거가 되는 코드·테스트 위치
- 외부 진입점 → 판단 → 상태 변경·외부 효과 → 응답·소비자의 흐름
- 달라진 계약 또는 불변식, 관련 검증 위치
- 읽은 범위와 아직 확인하지 못한 경계

이 정리는 작업 중 짧은 사실 메모로 유지한다. 전체 로그나 긴 사고 과정을 출력하지 않는다. PR 설명은 의도에 대한 자료이며 실제 동작을 입증하지 않는다.

## 3. 필요한 맥락 확보

Root 및 변경 경로에 적용되는 `AGENTS.md`를 읽고 연결된 상세 문서 중 관련 문서를 확인한다. CI/CD·Docker·배포는 물리적 경로와 관계없이 Infra 지침을 적용한다. 다음은 탐색 시작점이며 규칙을 이 스킬에 복제하지 않는다.

| 변경의 의미 | 추가 확인할 문서 |
| --- | --- |
| 계층·저장소·트랜잭션·외부 연동·화면 상태 흐름 | 해당 Stack의 `docs/development/<stack>/architecture.md` |
| 객체 생성·DTO·메서드 표현·예외·값 부재·로그 | 해당 Stack의 `docs/development/<stack>/conventions.md` |
| 비즈니스 판단·상태 전이·Entity·VO·Aggregate | `docs/development/backend/domain-responsibility.md` |
| 동작·계약·테스트 변경 | Backend 또는 Frontend의 `docs/development/<stack>/testing.md` |
| Infra 변경 | `docs/development/infra/conventions.md` |
| 용어·공개 literal 변경 | `docs/domain/glossary.md` |
| Calio의 AI 대화·Prompt·Tool 기능 | `docs/development/backend/ai-feature.md` |

후보를 판단하기 위한 질문을 먼저 정하고 해당 심볼의 정의·참조를 검색한다. 구현, 호출자, 소비자와 관련 테스트를 따라가며 답이 확보되면 탐색을 멈춘다.

- 상태 변경은 실제 변경 메서드와 모든 관련 외부 진입점을 확인한다. 호출자 하나에 검사 코드가 있다는 사실로 객체의 불변식 보호까지 입증하지 않는다.
- 트랜잭션·비동기는 호출 순서, 프록시 진입, 전파 설정, 취소·재시도 경로를 확인한다. 어노테이션이나 클래스 이름만으로 실행 경계를 판단하지 않는다.
- 계약 변경은 이름 검색뿐 아니라 직렬화 필드, enum literal, 오류 코드와 다른 Stack의 소비자를 확인한다.
- 프레임워크 동작에 판단이 달려 있으면 프로젝트 버전·설정과 공식 문서 또는 최소 재현으로 확인한다. 기억하는 최신 동작을 프로젝트에 그대로 적용하지 않는다.
- 검색 결과가 없다는 사실만으로 사용되지 않는 코드라고 단정하지 않는다. 동적 호출·설정 연결 여부가 미확인이면 한계로 남긴다.

지침 충돌은 문장과 적용 경로를 함께 기록한다. 코드의 기존 패턴이 문서와 다르면 차이를 확인하고, 문서의 권고를 절대 금지로 바꾸지 않는다.

## 4. 문제 후보 탐색

각 변경 단위를 아래 두 방향으로 검토한다. 한 방향을 먼저 끝냈다는 이유로 다른 방향을 생략하지 않는다.

**동작과 계약:** 변경된 입력·상태가 소비자에게 도달했을 때 결과가 어떻게 달라지는지 추적한다. 해당 변경에 관련된 실패, 값 부재, 경계 시각·수량, 중복 실행, 순서 역전과 부분 실패를 확인한다. 가능한 입력이나 상태에 의존하는 버그도 유효한 후보다. 발생 조건을 확인한다.

**설계와 책임:** 읽은 규칙에 비추어 판단과 상태 변경의 소유자가 적절한지 검토한다. 현재 테스트가 통과해도 명시적인 책임·경계 규칙을 위반하면 후보로 남긴다. 구조 개선 취향만으로 지적하지 않는다.

각 후보를 다음 형태의 짧은 사실 기록으로 남긴다.

> 후보 / 종류(동작·계약 또는 규칙 위반) / 도입한 변경 위치 / 발생 조건 또는 적용 규칙 / 근거 위치 / 반증할 보호 장치 / 검증 상태

후보를 만들 때부터 최종 지적 문구를 작성하지 않는다. 불명확한 부분을 가정으로 채워 확정하지 않는다.

## 5. 후보를 반증하고 검증하기

각 후보에서 “이 지적이 틀렸다면 어떤 코드나 계약이 그것을 보여줄까?”를 묻고, 실제로 그 근거를 찾는다. 같은 diff를 다시 읽거나 자신의 설명을 다시 평가하는 것만으로 검증을 끝내지 않는다.

1. **변경 귀속:** 이전 버전에도 같은 문제가 있었는지 확인한다. 새 호출 경로가 기존 결함을 노출했다면 그 연결을 입증한다. 순수 이동으로 기존 코드가 새 줄에 나타난 경우를 새 결함으로 세지 않는다.
2. **도달 가능성:** 지적한 입력·상태가 실제 경로로 도달 가능한지 확인한다. 앞단 검증, 호출 조건, DB 제약, DTO 변환 또는 도메인 메서드가 막는지 찾는다.
3. **규칙 적용:** 정확한 문장, 범위, 기본 선택과 예외를 확인한다. “검토한다”는 표현을 기계적인 금지로 해석하지 않는다.
4. **효과 확인:** 재현 가능한 입력·호출 순서 또는 명확한 코드 경로로 잘못된 결과를 입증한다. 설계 위반은 보호할 책임, 현재 소유자와 위반 경로를 제시한다.
5. **가장 작은 검증:** 관련 테스트의 assertion을 읽고 필요한 테스트·공식 문서·임시 재현을 선택한다. 테스트가 통과했다면 후보 시나리오를 실제 검증하는지 확인한다. 실패했다면 환경 오류나 기존 실패인지 구분한다.

명확한 코드 증거로 판단할 수 있는 후보에 실행 재현을 무조건 요구하지 않는다. 실행하지 않았으면 “코드 경로 확인”으로 표시한다. 검증을 위해 저장소 수정이나 운영 비밀값이 필요하면 가능한 분석을 마치고 한계를 알린다.

기계적 검사는 설정된 도구의 결과를 활용하고 동일 지적을 반복하지 않는다. 도구 도입이 예정되어 있다는 이유로 검사를 통과했다고 간주하거나, 이미 확인한 기능 오류를 숨기지 않는다. 순수 포맷 지적은 제외한다.

검증 결과는 **확인됨 / 반증됨 / 미확인**으로 구분한다. 확인된 후보만 지적으로 보고한다. 미확인 중 결정을 바꾸는 중요한 사항만 질문으로 남긴다. 수치형 자신감이나 지적 개수 목표를 사용하지 않는다.

지적 여부를 판단하기 모호하면 [판단 예시](references/finding-examples.md)의 관련 사례를 읽는다. 예시의 가정을 프로젝트 규칙으로 적용하지 않고, 실제 지침과 코드·계약으로 판단한다.

## 6. 누락 점검과 비용 관리

처음 정리한 변경 단위로 돌아가 아직 읽지 않은 중요 경계, 삭제·설정 변경, 다른 Stack의 소비자와 테스트를 빠뜨리지 않았는지 확인한다. 첫 지적을 찾았다는 이유로 나머지 변경 검토를 끝내지 않는다.

같은 원인·수정으로 해결되는 후보는 하나로 합친다. 검증이 끝난 후보의 탐색을 반복하지 않는다. 긴 로그와 파일 전체를 다시 로드하는 대신 필요한 부분과 원문 위치를 유지한다. 토큰·시간 제약으로 덜 본 범위는 결과에 표시하며 검토 완료로 바꾸지 않는다.

리뷰 종료 전에 대상 변경 여부를 확인한다. 새 변경이 들어왔으면 기존 결과와 섞지 않고 영향받은 분석을 갱신하거나 검토한 버전을 명시한다.

## 7. 결과 작성

한글로 중요한 지적부터 보고한다. 각 지적은 다음을 포함한다.

- 제목, 종류와 영향에 비례한 우선순위
- 이번 변경의 관련 코드 위치와 필요한 호출자·소비자 근거
- 구체적인 발생 조건 → 현재 결과 → 기대 결과, 또는 정확한 규칙과 위반 내용
- 수행한 검증과 최소 수정 방향

설계 지적을 보고하기 위해 장애 수준으로 과장하지 않는다. 관계없는 지적을 하나로 묶지 않는다. 긴 재작성 패치보다 문제를 해결하는 책임·경계 변경을 짧게 설명한다.

마지막에는 비교 범위·커밋, 검토한 변경 단위, 확인 질문과 검증 한계를 짧게 남긴다. 명세를 참조했다면 경로와 이번 PR 범위를 표시한다. 지적이 없다는 사실과 전체 검증 완료를 구분한다.

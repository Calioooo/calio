# 프론트엔드 아키텍처

## 목적

이 문서는 iOS frontend의 구조, 상태 소유와 데이터 흐름을 정하는 팀 검토용 초안이다.

Swift 작성 방식은 [conventions.md](conventions.md), 테스트는 [testing.md](testing.md)를 따른다.
Backend 계약과 도메인 용어는 Root `AGENTS.md`와 도메인 용어 사전을 따른다.

## 1. 코드 구성과 역할

- 현재의 `Views`, `ViewModels`, `Services`, `Repositories`, `Models` 구성을 기준으로 같은 책임의 코드를 묶는다.
- 각 디렉터리 내부는 기능별로 묶을 수 있으며, 기능 영역의 목록을 고정하지 않는다.
- 한 기능에서만 사용하는 타입을 사용 가능성이 있다는 이유로 공통 영역에 올리지 않는다.

| 역할 | 책임 |
| --- | --- |
| View | 화면 표시, 사용자 입력과 화면 전환을 수행한다. |
| ViewModel | 화면 데이터, 작업 상태와 사용자 액션의 처리 흐름을 관리한다. |
| Service | 입력을 요청 DTO로 변환하고, Repository 응답을 앱 모델과 기능별 오류로 변환한다. |
| Repository Protocol | 기능에 필요한 데이터 요청·응답 계약을 정의한다. |
| Repository Implementation | API 경로, HTTP method와 요청 데이터를 구성하여 `APIClient`를 호출한다. |
| APIClient | HTTP 통신, 인증 헤더, JSON 인코딩·디코딩과 공통 통신 오류를 처리한다. |
| Model | 앱 내부에서 사용하는 데이터와 표현에 필요한 값을 정의한다. |

- 기본 데이터 요청 흐름은 `View → ViewModel → Service → Repository Protocol → Implementation → APIClient`다.
- ViewModel에는 Service를, Service에는 Repository를 생성자로 전달한다. 모든 타입에 별도 Protocol을 만들지는 않는다.
- 날짜 계산과 입력 파싱처럼 통신이 없는 협력 객체에 Repository 계층을 추가하지 않는다.
- Service와 Repository는 화면의 로딩 상태, alert나 navigation을 직접 제어하지 않는다.

## 2. DTO와 앱 모델 경계

- API 요청·응답 DTO는 `Services/DTO`에, 화면에 전달하는 앱 모델은 `Models`에 둔다.
- Repository는 DTO를 반환하고 Service는 앱 모델로 변환한다. View와 ViewModel은 API DTO를 직접 소비하지 않는다.
- DTO는 전송 계약을 표현하고, 앱 모델은 화면에서 필요한 데이터를 표현한다. 둘의 필드가 같아도 역할을 혼합하지 않는다.
- Backend 응답이 변경되면 Repository와 Service 경계에서 처리하고, 화면에는 필요한 앱 모델 변경만 전달한다.
- 앱 모델의 화면용 식별자와 Backend 데이터 식별자를 구분한다. 화면용 ID를 API 변경 요청의 ID로 사용하지 않는다.

## 3. 화면 상태 소유

- 화면의 데이터 조회·변경 상태는 ViewModel이 소유하고, 외부 변경이 필요하지 않은 상태는 읽기 전용으로 노출한다.
- 입력 초안, 선택 항목과 sheet 표시처럼 화면에 국한된 상태는 View가 소유할 수 있다.
- 동일한 데이터를 여러 화면에서 공유해야 하면 공통 소유자가 관리하고, 하위 화면은 전달받은 상태와 액션을 사용한다.
- 함께 전이하는 상태는 enum 또는 명시적인 구조로 묶는다. 서로 독립적인 조회·저장 상태까지 하나로 합치지는 않는다.
- 최초 로딩, 빈 결과, 조회 실패와 기존 데이터가 있는 상태의 갱신 실패를 구분한다.
- 저장 실패 시 입력과 기존 데이터를 유지하고, 완료되지 않은 작업을 성공 상태로 표시하지 않는다.
- View는 navigation과 presentation을 수행한다. 작업 결과에 따른 전환 판단이 필요하면 ViewModel이 결과나 의도를 전달한다.

## 4. 비동기 작업과 캐시

- 비동기 요청은 `async/await`를 사용하고, 화면 상태를 관리하는 ViewModel은 `@MainActor`를 기본으로 한다.
- 화면 생명주기에 속한 작업은 `.task` 등을 사용한다. 별도로 생성한 Task는 취소와 결과 반영의 책임을 명확히 한다.
- 취소를 사용자에게 보여줄 일반 실패로 처리하지 않는다.
- 요청이 겹치거나 화면 세션이 바뀌면 요청 식별자나 세대 값 등으로 오래된 응답이 최신 상태를 덮어쓰지 않도록 한다.
- 중복 저장을 막고, 재시도 시 같은 변경이 중복 실행될 가능성을 확인한다.
- 캐시에는 조회 범위와 로딩·실패 상태를 함께 관리하고, 데이터 변경 후 영향을 받는 범위를 갱신하거나 무효화한다.
- 캐시나 임시 표시 데이터는 서버가 확인한 상태와 구분한다.

## 5. 날짜와 시간 경계

- API 시점 값과 화면의 날짜·현지 시각을 구분한다. 시점 인코딩·디코딩은 `APIJSONCoding`에 모은다.
- 화면 입력을 API 시간 계약으로 변환하는 책임은 Service에 두고, 화면에서는 표시 형식을 처리한다.
- 날짜 이동을 고정된 초 단위로 계산하지 않는다. 일정 시간대와 기기 표시 시간대를 구분한다.
- 종일 일정과 시간을 가진 일정의 경계 규칙을 혼합하지 않는다.

## 6. 구조 변경

- 공개 계약과 사용자 동작의 호환성을 유지하는 것과 내부 구조를 유지하는 것을 구분한다.
- 더 명확한 책임 배치가 필요하면 관련 구조를 개선한다. 기존 흐름 옆에 조건과 보조 타입을 계속 덧붙이는 것을 기본 해법으로 삼지 않는다.
- 새 계층, 공통 상태 저장소나 추상화는 실제 책임과 공유 필요가 있을 때 도입한다.

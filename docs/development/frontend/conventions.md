# 프론트엔드 구현 컨벤션

## 목적

이 문서는 Swift 및 SwiftUI 코드의 작성 방식과 표현을 정하는 팀 검토용 초안이다.

구조와 상태 소유는 [architecture.md](http://architecture.md), 테스트는 [testing.md](http://testing.md)를 따른다.  
코드 포맷은 팀에서 정한 formatter를 따르며, 들여쓰기와 줄 길이를 별도의 의미 규칙으로 반복하지 않는다.

## 1. 타입과 객체 구성

- 데이터와 입력 모델은 `struct`를 기본으로 하고, 공유되는 참조 상태가 필요한 객체는 `class`를 사용한다.
- 상속을 의도하지 않은 class는 `final`로 선언한다.
- 변경이 필요하지 않은 값과 의존성은 `let`으로 선언하고, 필수 의존성은 생성자로 전달한다.
- 내부 구현은 `private`으로 제한하고, 외부에서 읽기만 필요한 상태는 `private(set)`으로 노출한다.
- 하나의 타입에서만 사용하는 보조 타입은 내부 타입이나 같은 파일의 비공개 타입을 검토한다.
- 값의 동등성, 식별과 직렬화가 필요한 경우에만 해당 Protocol을 채택한다.

## 2. SwiftUI 구성

- View가 생성하고 소유하는 ObservableObject는 `@StateObject`, 전달받아 관찰하는 객체는 `@ObservedObject`로 선언한다.
- 화면 내부의 값 상태는 `@State`, 상위 소유자의 값을 수정해야 할 때는 `@Binding`을 사용한다.
- `body`는 상태에 따른 UI 구성에 집중한다. 네트워크 요청이나 상태 변경을 직접 실행하지 않는다.
- 하위 View는 필요한 데이터와 액션만 전달받는다. 단순 표시 컴포넌트에 전체 ViewModel을 전달하지 않는다.
- 의미 있는 UI 영역은 별도 View나 computed property로 분리하되, 줄 수를 줄이기 위한 분리는 하지 않는다.
- 반복 표시 항목은 데이터의 안정적인 식별자를 사용한다. 렌더링할 때마다 새 UUID를 만들지 않는다.
- 앱 UI 색상은 프로젝트 컬러 팔레트에 정의된 색상을 용도에 맞게 사용하고, 화면에서 임의의 색상값을 반복 정의하지 않는다.
- 반복되는 UI 스타일은 같은 역할과 의미일 때 재사용하며, 의미가 다른 스타일은 강제로 공통화하지 않는다.
- 아이콘만 있는 액션에는 접근성 이름을 제공하고, 중요한 정보나 상태를 색상만으로 전달하지 않는다.
- 글자 크기 확대와 시스템의 모션 감소 설정을 고려한다.

## 3. 함수 구성과 네이밍

- 타입, 함수와 변수의 이름은 동작과 대상의 의미를 드러내고, 도메인 용어는 용어 사전을 따른다.
- boolean은 `is`, `has`, `can` 등으로 판단 의미를 드러내고, 컬렉션은 복수형으로 표현한다.
- 함수는 하나의 명확한 목적을 가진다. 조회와 변환 함수에는 저장이나 독립적인 상태 변경을 넣지 않는다.
- 함수 분리는 줄 수가 아니라 책임과 의미를 기준으로 판단한다.
- 같은 의미의 로직이 반복되면 추출하되, 코드 모양만 비슷한 서로 다른 책임은 공통화하지 않는다.
- 실패·종료 조건은 `guard`와 early return으로 드러내고, 복잡한 조건은 의미 있는 이름으로 표현한다.
- 보조 함수와 computed property는 독립된 의미가 있거나 상위 흐름을 명확히 할 때 추출한다.
- 컬렉션 변환과 반복문은 부수 효과, 처리 순서와 결과를 더 쉽게 이해할 수 있는 방식을 선택한다.

## 4. DTO와 값 부재

- DTO 이름에는 요청·응답과 기능을 드러내고, API 필드명이 Swift 표현과 다르면 `CodingKeys`로 연결한다.
- API 계약에서 부재가 허용되는 값만 Optional로 표현한다. 디코딩 오류를 피하기 위해 필수값을 Optional로 바꾸지 않는다.
- 필수 계약 필드를 `try?`로 읽고 정상적인 기본값으로 대체하지 않는다.
- 목록의 빈 결과는 빈 컬렉션으로 표현하고, 미조회·조회 실패와 혼합하지 않는다.
- Optional은 `guard let`이나 `if let`으로 안전하게 해제한다. 값 부재는 계약에 따라 처리하며, 기본값은 의미가 정의된 경우에만 사용한다. 사용자 입력과 외부 응답을 강제 해제하지 않는다.
- 기본값은 부재 시 표현이 정의된 경우에만 사용한다. 필수값 누락이나 알 수 없는 비즈니스 상태를 기본값으로 숨기지 않는다.
- 알 수 없는 enum·결과 타입은 계약에 맞는 디코딩 실패나 명시적인 미지원 표현으로 처리하고, 기존 값으로 조용히 변환하지 않는다.

## 5. 입력 검증과 오류 처리

- 필수값, 길이와 형식은 입력 경계에서 검증하고, 저장 가능 여부와 오류 안내가 같은 검증 기준을 사용하도록 한다.
- 입력 초안과 요청값을 구분하고, 공백 정리 등 입력 정규화는 의미가 정해진 경우에만 수행한다.
- 네트워크, 인코딩·디코딩과 Backend 비즈니스 실패를 구분하여 기능별 오류로 변환한다.
- Backend 비즈니스 실패의 분기는 안정적인 `errorCode`를 기준으로 하고, 메시지 문자열을 파싱하지 않는다.
- 오류 변환 시 분기에 필요한 코드와 상태를 보존하고, 사용자 문구는 내부 진단 정보와 구분한다.
- 오류는 복구, 재시도 또는 의미 있는 변환을 수행하는 위치에서 처리한다.
- 알 수 없는 실패는 공통 오류로 안내하며, 빈 결과나 성공으로 숨기지 않는다.

## 6. 설정, 인증과 로그

- API 주소와 환경별 설정은 기존 설정 경계에서 관리하고, 화면과 기능별 코드에 반복해서 넣지 않는다.
- 인증 토큰은 Keychain 같은 보안 저장소를 사용하고, 요청 인증 헤더는 공통 통신 경계에서 처리한다.
- 인증 토큰, 인증 코드와 원문 대화 등 민감 정보는 로그나 진단용 화면에 직접 노출하지 않는다.
- 비동기 작업과 외부 요청의 중요한 결과·실패는 필요한 작업 식별자와 함께 추적할 수 있도록 기록한다.
- 같은 실패를 여러 계층에서 중복 기록하지 않고, 사용자 안내와 개발용 진단 로그를 구분한다.

## 7. 날짜와 시간 처리

- 날짜 단위 비교·그룹화에는 기준 `Calendar`와 `TimeZone`을 명확히 하고, 시점과 날짜를 구분한다.

# 백엔드 구현 컨벤션

## 목적

이 문서는 backend 코드의 작성 방식과 표현의 일관성을 정한다.

계층, 영속성과 트랜잭션 경계는 [architecture.md](architecture.md),  
비즈니스 책임 배치는 [domain-responsibility.md](domain-responsibility.md)를 따른다.  
코드 포맷은 프로젝트에 설정된 formatter를 따른다.

## 1. 객체 생성

- 단순한 객체 생성은 생성자를 사용한다.
- 생성 목적이나 서로 다른 생성 조건을 이름으로 구분해야 할 때는 정적 팩토리를 사용한다.
- 생성에 필요한 필수값은 생성 시점에 전달한다. 객체 생성 후 여러 setter를 호출해 유효한 상태를 완성하지 않는다.
- JPA 기본 생성자는 프레임워크가 요구하는 최소 가시성으로 둔다.
- Value Object는 불변으로 작성하고 값의 동등성을 표현한다.

## 2. DTO 구성과 변환

- Request와 Response DTO는 해당 기능 영역의 `controller/dto`에 둔다.
- 외부 API 요청·응답 DTO는 해당 기능 영역의 `client/dto`에 둔다.
- 여러 Application Service가 공유하는 데이터 타입은 해당 기능 영역의 `service/dto`에 둔다. 하나의 클래스에서만 사용하는 타입은 내부 타입을 검토한다.
- 불변 데이터 전달 객체는 `record`를 기본으로 사용한다.
- Response DTO 변환은 DTO의 `static from(...)`을 기본으로 하며, 이를 위한 전역 mapper 레이어는 두지 않는다.
- Request DTO는 입력값을 표현하며, 도메인 객체의 생성과 변경은 Application Service가 도메인 생성자나 행위를 호출해 수행한다.
- DTO 변환은 필드 매핑과 표현용 값 조합에 한정한다. 정책 판단, Repository 조회와 외부 호출을 넣지 않는다.

## 3. 메서드 구성과 네이밍

- 타입은 import하여 단순 이름으로 사용한다. 이름이 충돌해 구분이 필요한 경우에만 코드에서 완전한 클래스명을 사용한다.
- 메서드 이름은 동작, 대상과 결과의 의미를 드러낸다.
- 도메인 용어는 [docs/domain/glossary.md](../../domain/glossary.md)의 정의와 일치시킨다.
- 조회 메서드는 단건·목록 여부와 값이 없을 때의 동작을 명확히 표현한다.
- 메서드는 하나의 명확한 목적을 가진다. 조회 메서드는 상태를 변경하지 않으며, 변경 메서드에 독립적인 조회 기능을 혼합하지 않는다. 변경 결과를 반환하는 것은 허용한다.
- boolean 값과 판단 메서드는 `is`, `has`, `can` 등 의미에 맞는 표현을 사용한다.
- 도메인 변경 메서드는 범용 setter보다 변경의 비즈니스 의미를 드러내는 이름을 사용한다.
- 함수 분리는 줄 수가 아니라 책임과 의미를 기준으로 판단한다.
- 같은 의미의 로직이 반복되면 추출하되, 코드 모양만 비슷한 서로 다른 책임은 공통화하지 않는다.
- 보조 메서드는 독립된 의미가 있거나 상위 흐름을 명확하게 만들 때 추출한다.
- 실패 조건과 종료 조건은 guard clause와 early return으로 드러내되, 흐름이 오히려 복잡해지면 강제하지 않는다.
- Stream과 반복문은 처리 순서, 부수 효과와 결과를 더 쉽게 이해할 수 있는 방식을 선택한다.

## 4. 입력 검증과 예외 처리

- 필수값, 길이와 형식 등 요청 입력 제약은 Request DTO의 Bean Validation을 기본으로 표현한다.
- 도메인 객체가 반드시 지켜야 하는 조건은 요청 검증 여부와 무관하게 도메인에서 보호한다.
- 예상 가능한 비즈니스 실패는 `CalioException`과 `ErrorCode`를 기본으로 표현한다.
- 개별 예외 클래스는 호출자가 해당 실패 유형을 구분해야 하거나 별도의 의미와 데이터를 표현해야 할 때 검토한다.
- HTTP status와 오류 응답 변환은 전역 예외 처리기에서 일관되게 수행한다.
- 예상하지 못한 내부 오류는 전역 예외 처리기에서 공통 internal error 응답으로 변환하며, 내부 구현 정보를 노출하지 않는다.
- Controller에서 비즈니스 예외를 개별적으로 잡아 응답으로 변환하지 않는다.
- 예외는 복구, 보상 또는 의미 있는 변환이 필요한 위치에서만 처리한다.
- 기술 예외를 변환할 때는 원인을 보존하되 내부 구현과 민감 정보를 응답에 노출하지 않는다.
- 오류 메시지는 설명용이며, 클라이언트의 분기 기준은 안정적인 `errorCode`다.

## 5. 컬렉션과 값 부재

- 외부에서 전달받은 컬렉션을 보관할 때는 필요한 경우 방어적으로 복사한다.
- 내부 상태를 나타내는 컬렉션은 외부 코드가 직접 변경하지 못하도록 노출한다.
- 목록 조회 결과가 없으면 `null` 대신 빈 컬렉션을 반환한다.
- 단건 조회에서 값 부재가 정상적인 결과라면 `Optional` 반환을 검토한다.
- `Optional`은 반환 계약에 사용하고 Entity 필드, DTO 필드와 메서드 매개변수에는 기본적으로 사용하지 않는다.
- 값 부재가 실패인 유스케이스는 명시적인 예외로 표현한다.
- 기본값은 비즈니스나 계약에서 정의된 경우에만 사용한다. 알 수 없는 상태나 오류를 정상적인 기본값으로 대체하지 않는다.
- API의 nullable 여부는 내부 구현 편의가 아니라 공개 계약을 기준으로 결정한다.

## 6. Spring 구성과 로그

### Spring 구성

- 의존성 주입은 생성자 주입을 사용한다.
- 의존성은 필수 여부가 드러나도록 선언하고, 변경할 필요가 없는 참조는 `final`로 둔다.
- 관련 설정값은 `@ConfigurationProperties`로 묶어 관리한다.
- 해당 client에 전속된 properties는 해당 기능 영역의 `client` 아래에 둔다.
- Spring Bean을 도메인 객체의 필드에 직접 주입하지 않는다.

### 로그

- 운영상 중요한 작업의 결과, 상태 전이와 실패를 추적할 수 있도록 기록한다.
- 로그에는 필요한 작업 식별자, 대상 식별자와 결과를 포함한다.
- 토큰, 인증 정보와 원문 사용자 입력 등 민감 정보를 직접 기록하지 않는다.
- 정상 흐름, 진단 정보와 실패를 구분해 로그 레벨을 선택한다.
- 같은 예외를 여러 계층에서 반복적으로 기록하지 않는다. 처리 결과와 원인을 가장 잘 설명할 수 있는 위치에서 기록한다.
- 비동기 작업과 외부 API 연동은 처리 결과와 실패 원인을 추적할 수 있도록 로그를 남긴다.
